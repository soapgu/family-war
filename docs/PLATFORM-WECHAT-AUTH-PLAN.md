# 儿童学习游戏平台与微信认证规划

> 状态：产品与技术可行性规划，暂不实施
>
> 涉及项目：统一入口、`family-war`、`that-math-things` 及未来子应用
>
> 相关文档：[多应用平台路由改造方案](./ROUTING-MIGRATION-PLAN.md)

## 1. 规划目标

将现有和未来的寓教于乐应用组织为一个完整的网站产品，而不是多个彼此无关的网站：

```text
统一学习平台
├── 总入口
├── family-war：家庭互动游戏
├── that-math-things：纯前端数学学习工具
├── 未来的识字应用
├── 未来的英语应用
└── 个人中心与家庭管理
```

总入口负责：

- 展示、介绍和导航各子应用；
- 提供统一登录和退出；
- 选择当前使用者档案；
- 展示个人中心、家庭成员和学习记录入口；
- 为需要身份的子应用提供统一会话；
- 允许不需要身份的子应用继续匿名使用。

该产品定位有利于微信开放平台网站应用的申报：微信登录服务于一个完整的儿童学习与亲子互动平台，各子应用是同一产品中的功能模块。

## 2. 产品定位建议

建议对外描述为：

> 面向家庭场景的儿童学习与亲子互动平台，提供数学练习、家庭知识竞赛、单词默写等寓教于乐功能。家长可以使用微信登录并管理家庭档案，儿童可以在不同应用中学习和游戏。

申请、备案和网站实际内容应保持一致。不能以儿童学习平台名义申请后，再将同一微信 AppID 用于与该产品无关的网站。

## 3. 名称建议

### 3.1 中文产品名候选

- 童学乐园
- 家庭学习岛
- 亲子成长屋
- 小小探索家
- 家庭智慧乐园
- 一起学一起玩

名称选择标准：

- 能覆盖学习、游戏和亲子互动，不局限于某一个子应用；
- 儿童和家长都容易理解、记忆；
- 不使用容易产生教育资质误解的表述；
- 正式确定前检查域名、商标和微信平台重名情况；
- 网站名称、备案名称和微信应用名称尽量保持一致。

### 3.2 内部工程名候选

- `kids-hub`
- `family-learning-hub`
- `main-portal`

“Main Page”可以作为临时代号，但不建议作为正式产品名称。

## 4. 统一站点结构

目标使用一个主域名和路径式子应用：

```text
https://kids.example.com/                    总入口
https://kids.example.com/family-war/         家庭互动游戏
https://kids.example.com/that-math-things/   数学学习工具
```

HTTP API、认证和 Socket.IO 的详细路径规范见《多应用平台路由改造方案》。核心约定为：

```text
前端页面：/{app}/
应用 API：/api/{app}/
统一认证：/api/auth/
实时连接：/socket/{app}/
```

`that-math-things` 当前是纯前端应用，不需要自己的 API 命名空间，也不强制要求登录。

## 5. 微信扫码登录可行性

计划采用微信开放平台“网站应用微信登录”，而不是自行解析二维码或使用非官方登录接口。

标准流程：

1. 用户在总入口点击微信登录；
2. 平台服务端生成带随机 `state` 的微信授权地址；
3. 浏览器展示微信登录二维码；
4. 用户扫码并确认授权；
5. 微信回调平台服务端，携带一次性 `code` 和原始 `state`；
6. 服务端校验 `state`，再用 `code` 换取微信访问凭证；
7. 服务端读取微信开放身份及授权范围内的基本资料；
8. 创建或更新平台账户；
9. 写入本站 Session Cookie；
10. 用户回到总入口并选择当前使用者档案。

### 5.1 可获得的身份标识

预期使用：

- `openid`：用户在当前微信网站应用下的唯一标识；
- `unionid`：满足微信 UnionID 条件时，用于同一开放平台主体下跨应用统一身份；
- 微信授权接口实际返回的昵称、头像等基本资料。

微信开放平台不会向网站提供用户个人资料中可见、可修改的“微信号”。产品文案中的“微信 ID”应准确表述为开放平台 `openid` 或 `unionid`。

不要把 `openid` 或 `unionid` 作为公开用户 ID 返回给浏览器和其他用户。平台应生成自己的内部账户 ID。

### 5.2 应用申报方式

建议只申报一个完整的网站应用，例如：

```text
应用名称：待定的正式平台名
应用主页：https://kids.example.com/
授权回调域：kids.example.com
实际回调：https://kids.example.com/api/auth/wechat/callback
```

申请时应展示可访问的总入口、产品说明、主要子应用、隐私政策和用户协议。授权回调域、正式域名和实际回调必须一致。

## 6. 账户、档案与游戏角色

微信扫码认证的是微信账户持有人，实际使用子应用的可能是家长或孩子。因此必须拆分以下概念：

```text
平台账户
└── 家庭
    ├── 家长档案
    ├── 儿童档案 A
    └── 儿童档案 B

儿童档案 A
└── 某局游戏角色：儿子 / 玩家 1
```

### 6.1 平台账户

代表完成微信扫码登录的人，保存：

```js
{
  id: 'account_...',
  wechatOpenId: '仅服务端保存',
  wechatUnionId: '仅服务端保存或为空',
  nickname: '微信授权资料',
  avatarUrl: '微信授权资料',
  createdAt: '...',
  lastLoginAt: '...'
}
```

### 6.2 家庭档案

代表实际使用平台的人：

```js
{
  id: 'profile_...',
  familyId: 'family_...',
  name: '大宝',
  type: 'child',
  avatar: '...',
  permissions: ['family-war:play']
}
```

一个家长微信账户可以管理多个儿童档案；未来也可以允许爸爸和妈妈的两个微信账户共同管理一个家庭。

### 6.3 游戏角色

`爸爸`、`妈妈`、`儿子` 是当前游戏中的角色，不应继续承担永久用户 ID 或平台账户的职责。长期模型应区分：

```text
账户：微信登录主体
档案：实际使用者
角色：某个子应用或某局游戏中的身份
```

机器人继续保留固定的内部身份 `__robot__`，不对应平台账户。

## 7. 子应用共享身份

登录信息不通过链接参数在子应用之间传递。统一认证服务应设置作用域覆盖整个站点的 Cookie：

```text
Cookie 名称：平台专用名称
Path=/
HttpOnly
Secure
SameSite=Lax
```

子应用前端通过以下接口获取当前身份：

```text
GET /api/auth/me
```

示例响应：

```json
{
  "authenticated": true,
  "account": {
    "id": "account_123",
    "nickname": "微信昵称",
    "avatarUrl": "https://example.com/avatar"
  },
  "profile": {
    "id": "profile_child_1",
    "name": "大宝",
    "type": "child"
  }
}
```

禁止采用：

```text
/family-war/?openid=xxx&nickname=xxx
/family-war/?token=长期登录令牌
```

需要保护数据的后端接口必须验证 Cookie 对应的服务端会话。前端读取 `/api/auth/me` 只用于界面展示，不能代替后端鉴权。

## 8. 匿名子应用

统一认证不代表所有子应用都强制登录。

`that-math-things` 可以继续作为纯前端匿名应用：

- 未登录：所有现有纯前端功能正常使用；
- 已登录：可以选择展示当前档案、返回总入口等平台信息；
- 未来增加保存进度时，再接入平台 API；
- 不为未来尚不存在的后端提前创建 `/api/that-math-things/`。

是否要求登录应由具体功能决定：

| 功能 | 匿名 | 登录后 |
|---|---:|---:|
| 浏览总入口和应用介绍 | 支持 | 支持 |
| 使用纯前端数学工具 | 支持 | 支持 |
| 保存个人学习进度 | 不支持 | 支持 |
| 跨设备同步 | 不支持 | 支持 |
| 家庭管理 | 不支持 | 支持 |
| 家长查看儿童记录 | 不支持 | 支持 |

## 9. 认证服务设计

建议将统一认证实现为平台级服务，而不是放进某个子应用内部。

基础接口：

```text
GET  /api/auth/wechat
GET  /api/auth/wechat/callback
GET  /api/auth/me
POST /api/auth/logout
POST /api/auth/profile/select
```

认证服务负责：

- 微信 OAuth 状态生成和校验；
- 微信凭证交换；
- 账户创建、更新与绑定；
- Session 创建、验证、续期和撤销；
- 当前家庭档案选择；
- 向子应用提供可信的内部身份验证能力。

子应用可以通过内部认证接口或共享 Session 存储验证会话。初期用户量很小，可以先使用 SQLite；是否引入 Redis 留到实施阶段决定。

### 9.1 `family-war` 接入

HTTP API 和 Socket.IO 握手都应验证平台会话。服务端使用验证得到的档案 ID 和名称，不能相信客户端自行提交的用户 ID 或昵称。

现有管理员密码认证与平台用户认证不是同一概念。迁移初期可以并存，后续再决定是否整合成平台权限：

```text
family-war:play
family-war:admin
platform:family-manage
```

## 10. 安全要求

- `AppSecret` 只保存在服务端环境变量或密钥管理系统；
- OAuth `state` 必须随机、短期有效且一次性使用；
- 不接受客户端提交的 `openid` 作为登录凭证；
- Session ID 使用密码学安全随机数，服务端只保存必要信息；
- Cookie 使用 `HttpOnly`、`Secure` 和适当的 `SameSite`；
- 修改状态的接口增加 CSRF 防护或严格校验 `Origin`；
- 设置登录、回调和会话验证的限流；
- 日志不记录微信访问凭证、完整 Session ID 或 AppSecret；
- 提供退出登录和会话撤销能力；
- 用户数据、隐私政策和实际收集范围保持一致；
- Socket.IO 连接和普通 HTTP API 使用同一可信身份来源。

## 11. 部署与审核前提

正式接入前需核实微信开放平台当期规则。通常需要准备：

- 可申请网站应用的企业或组织主体；
- 有效的主体资料和授权联系人；
- 正式域名；
- 中国大陆服务器对应的网站备案；
- HTTPS；
- 可公开访问并与申报内容一致的网站；
- 网站 Logo、简介、应用截图等审核材料；
- 用户协议、隐私政策和必要的数据处理说明；
- 微信开放平台要求的开发者资质认证和网站应用审核。

一台服务器部署多个 Web 项目不影响微信认证。微信关注的是应用、主体、域名、回调域和实际用途的一致性，不要求一个应用独占一台服务器。

## 12. 成本估算

以下只用于预算，不视为报价；活动价格和微信平台规则以实际购买、申请页面为准。

### 12.1 已有合适主体且自行开发

| 项目 | 估算 |
|---|---:|
| 阿里云活动服务器 | 约 99～199 元/年 |
| 域名 | 首年约 30～100 元，续费约 70～120 元/年 |
| HTTPS | 可使用免费证书 |
| DNS、备案 | 通常无直接费用 |
| 微信开放平台认证审核 | 历史常见为 300 元/次，以控制台为准 |
| 少量备份 | 0～100 元/年 |

可将首年现金预算暂按约 500～1000 元准备。长期预算需要考虑服务器活动续费规则和微信认证有效期。

### 12.2 没有合适主体

主体是主要门槛。若仅为该项目注册并维护企业，还可能产生代理记账、报税、注册地址和银行账户等持续成本，不建议只因微信登录而仓促成立企业。

### 12.3 开发投入

粗略估算：

- 最小可用版本：约 5～8 个开发日；
- 包括家庭档案、权限、异常处理、测试和部署的完整版本：约 10～18 个开发日；
- 自行开发主要是时间成本；
- 外包价格会因 UI、合规材料、部署和维护范围产生较大差异。

## 13. 无法接入微信时的备用方案

如果暂时没有合适主体，可以先实现“家庭二维码登录”：

1. 电脑生成短期、一次性二维码；
2. 手机扫码打开本站确认页；
3. 选择家庭身份并输入 PIN，或由已绑定手机确认；
4. 服务端通知电脑端并建立本站 Session。

该方案可以使用微信扫一扫打开网页，但微信只作为二维码扫描器和浏览器，无法获得真实微信 `openid`、昵称或头像。

无论最终使用微信登录还是家庭二维码登录，都应复用同一套平台账户、家庭档案、Session 和子应用鉴权模型。身份提供方不应侵入游戏业务逻辑。

## 14. 分阶段路线

### 阶段一：产品准备

1. 确定正式产品定位和候选名称；
2. 确认企业或组织主体是否满足网站应用申请条件；
3. 检查域名、商标、备案名称和微信应用名称可用性；
4. 确定总入口的信息架构；
5. 明确匿名功能和登录后功能的边界。

### 阶段二：平台基础

1. 建立总入口；
2. 按路由改造方案统一公网路径；
3. 建立账户、家庭和档案模型；
4. 建立与身份提供方无关的 Session 服务；
5. 先使用开发环境测试登录适配器验证完整业务流程。

### 阶段三：微信接入

1. 完成域名、HTTPS、备案和公开页面；
2. 准备隐私政策、用户协议和审核材料；
3. 申请微信开放平台网站应用；
4. 实现并测试 OAuth 回调；
5. 完成账户绑定、退出和异常处理。

### 阶段四：子应用接入

1. `family-war` 接入平台 HTTP 会话；
2. `family-war` Socket.IO 接入握手鉴权；
3. 将平台档案与游戏角色分离；
4. `that-math-things` 保持匿名可用，仅按需要展示平台身份；
5. 后续应用按是否存在后端、是否需要身份分别接入。

## 15. 实施前需要确认的问题

- 正式产品名称是什么；
- 当前是否已有可用于微信开放平台认证的主体；
- 正式域名和备案主体如何安排；
- 微信账号代表家长，还是也允许其他成年人建立账户；
- 一个家庭是否允许多个家长账户共同管理；
- 儿童档案是否需要 PIN 或家长确认才能切换；
- 哪些 `family-war` 功能必须登录；
- 现有管理员密码认证何时迁移到平台权限；
- 用户和 Session 使用 SQLite、Redis 还是其他存储；
- 是否需要学习进度、游戏记录、账号注销和数据导出。

这些问题在正式开发前形成明确决策即可，当前阶段不要求立即确定。
